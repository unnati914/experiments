Proof Check: show the proof, or ask, or say no.

A tiny version of the idea, built on Indian tax rules. Every answer is built step by step from written rules. If one missing fact could change the answer, it asks for that fact. If the question is outside its rules, it refuses instead of guessing.

01 · ASK, DON'T REFUSE

Find the one missing fact

When a proof fails only because a fact is missing, try every value of that fact. If the answer doesn't change, answer anyway. If it does, ask just that one question. Fewer refusals, same rigour. (Working in the demo: try the 80D questions.)

02 · "WHY NOT?"

Counterexamples people can read

When a claim is false, show the smallest change that would make it true: "You'd get the full ₹50,000 only if you or your spouse were 60+." A refusal becomes something the user can act on.

03 · LAW-CHANGE REPORT

See what a new rule breaks

Give every rule an effective date. On Budget day, re-run all saved questions on the old and the new rules and list the answers that change, before customers find out.

04 · PROOF RECEIPT

A proof a CA can sign

Turn the formal proof into a one-page receipt in plain English, each step linked to the exact rule text. Auditors and CAs check the receipt, not the Lean code.

05 · BOUNDARY TESTS

Tests written from the rules

For every number in a rule, generate tests at limit −1, limit and limit +1, and one test per exception. Run them before any rule change ships. Most of the 16 cases here came from this pattern.

06 · INSTRUCTION FIREWALL

Documents are facts, not orders

Parse uploads into typed facts before the prover sees them. Any instruction found in a document is logged and ignored. Case 14 tests this.

A sketch of how the 80C rule could be written so a machine can check it. Not run on this page.

-- Section 80C, FY 2025-26: capped at ₹1,50,000, and zero in the new regime
def cap80C : Nat := 150000

def deduction80C (invested : Nat) (newRegime : Bool) : Nat :=
  if newRegime then 0 else min invested cap80C

theorem deduction80C_le_cap (x : Nat) (b : Bool) :
    deduction80C x b ≤ cap80C := by
  unfold deduction80C
  split
  · exact Nat.zero_le _
  · exact Nat.min_le_right _ _

Challenge

"Proved", but the rule was written wrong

A proof is only as good as the formal rule. If the model that turns law into Lean misreads one exception, every answer built on it is confidently wrong.

How I'd solve it

Test the rules, not just the answers

Boundary tests generated from each rule; two independent formalisations of the same rule compared on thousands of inputs; any disagreement goes to a tax or legal expert.

Challenge

Laws change and clash

Budgets change limits every year. India's new Income-tax Act renumbered sections from April 2026 (80C became s.123). Circulars and court rulings add more.

How I'd solve it

Versioned rules with dates

Every rule carries "valid from / until". Questions are answered on the right version, the law-change report shows what moved, and the checker refuses when no version covers the date (case 16).

Challenge

Too many "I can't prove that"

A system that refuses often is safe but users drift back to chatbots that always answer.

How I'd solve it

Measure refusals like errors

Track refusal rate next to accuracy on every release. Turn refusals into one clear question where possible (cases 5 and 7), and answer when the missing fact can't change the result (case 8).

Challenge

Messy and hostile input

Scanned forms, wrong numbers, negative amounts, and documents with hidden instructions aimed at the AI.

How I'd solve it

Typed facts before the prover

Validate every value, reject what doesn't parse (case 15), and never take instructions from a document (case 14). Keep an attack test set that grows with every incident.

Challenge

People can't read Lean

A machine-checked proof doesn't build trust if the user, the CA or the regulator can't follow it.

How I'd solve it

Plain-English proof receipts

Each step in one sentence, with the rule it used, like the steps in this demo. Exportable for audits.
